# Wanta 默认访问权限整体审计

审计日期：2026-09-08。代码基线：`8d32e41176a63ea358e9652d3e347f9632fb8863`。

审计目标：面向懂 IT 的用户，尽量少打断正常工作，同时降低误操作造成不可逆重大损失、影响他人或共享资源的概率。本文不以构建强隔离沙箱、抵御主动恶意本地代码为目标。

## 1. 总体结论

**产品方向合理，但当前实现还没有形成与目标匹配的统一权限模型。建议做一次边界收敛，而不是继续围绕命令写法添加特例。**

默认访问已经相当宽松：普通命令、脚本、项目外具体文件读写、网络访问大多自动批准。因此，问题不在于总体放行率太低，而在于：

1. **确认与实际后果关联不足。** 有的无副作用操作被拒绝，有的会造成重大损失的操作自动通过。
2. **实际保护取决于执行通道。** 同一个操作经 OpenCode、Claude ACP、通用 API、连接器或浏览器执行，可能得到不同处理。
3. **系统把路径名称、命令名称和工具归属当成了风险依据，却缺少资源归属、影响范围、恢复能力和既有授权信息。**

当前功能适合被准确描述为“默认自动执行，针对已识别的部分敏感操作提供确认提醒”。它不能可靠承诺“高风险操作一定会确认”，尤其不能承诺“不同智能体具有相同保护”。

最先应修复的是实际 ACP 请求的归一化错误。这是确定的实现缺陷，不涉及产品该宽松还是严格的取舍。随后应把有限的保护预算集中在真实数据丢失、共享资源破坏和错误账户/环境上，同时减少环境变量检查、依赖来源和普通发布流程中的无意义摩擦。

## 3. 当前机制实际如何工作

### 3.1 本地路径

OpenCode 把 bash、edit、external_directory 等请求交给 Wanta；部分 OO 调用有原生快速放行路径。ACP 则仅将原生智能体发出的权限请求转给 Wanta。**原生智能体不请求审批的操作，不会因为共享分类器存在就自动经过它。**

共享分类器的大致顺序：

1. 特殊诊断任务范围限制。
2. 外部智能体的 Wanta host tool 去除重复审批。
3. OO 凭证引用、环境转储、运行时配置变更等硬拒绝。
4. 纯 OO 调用自动允许。
5. 完全访问自动允许剩余本地请求。
6. 敏感资源确认；已识别高风险命令确认，但部分清理操作例外放行。
7. 受限依赖安装与已有会话授权放行。
8. 所选项目 `.env` 写入、依赖变更和宽范围编辑等确认。
9. 其余 command/path/edit/local/network 全部允许。

“trustedProjectRoot”因此主要用于若干例外和上下文识别，**并不是默认访问的文件系统围栏**。项目外普通读写本来就可自动允许。这符合宽松定位，本身不应算漏洞。

依据：[本地决策](../../electron/chat/local-access-policy.ts#L193)、[OpenCode 配置](../../electron/agent/config.ts#L61)。

### 3.2 业务能力与浏览器

Link/OO guard 主要控制运行时、团队、连接身份、允许的能力、部分路径和参数；服务端还可以按账户及 Action 权限拒绝操作。这些机制回答“用谁的身份、能调用什么”。

本次检查的本地 Link 执行链没有统一的“该请求是否会大规模不可逆删除”决策门。浏览器则明确依赖智能体行为提示：敏感或有后果的操作要求用户自己完成，而 `click` 执行入口并不判断业务后果。

这两类机制各有合理用途，但尚未组成贯穿通道的误操作保护。

## 4. 主要发现

优先级定义：P1 为直接削弱核心保护承诺、应优先处理；P2 为明显的产品摩擦、语义偏差或后续事故放大因素。本文没有把“允许任意代码”本身列为需要全面封禁的 P0。

### F1 · P1：真实 Claude ACP 命令会丢失操作类型，绕过共享命令保护

**已复现，置信度高。**

`onAcpPermissionRequest()` 把 `toolCall.title` 当成 `request.action`。`permissionRequestKind()` 则只用 action 是否包含 `bash`、`command`、`shell` 等子串来识别命令。

已安装 Claude ACP 的 Bash payload 实际为：

```text
title: "rm -rf /work/shared/client-data"
kind: "execute"
rawInput: { command: "rm -rf /work/shared/client-data" }
```

Wanta 忽略了这里的 `kind: execute`，把标题复制成 action。它不包含上述关键词，于是成为 `local`。命令风险检查和 OO 硬拒绝只在 `command` 分支触发，随后普通 local 自动允许。

探针用真实包的 `toolInfoFromToolUse()` 生成 payload，再按当前转换代码构造共享请求，验证此命令返回 `allow`；同一命令以 `action: bash` 输入会返回 `prompt`。这不是仅靠猜测某个未来 Agent 格式得出的结论，但尚未执行真实删除会话。

现有跨智能体测试使用 `Bash`、`Run command` 等人为构造标题，无法发现这个问题。未知 action 同样默认变为 `local`，让归一化失败表现得和正常放行一样。

**建议：** 使用原生结构化 kind、可信工具身份、关联的完整 tool-call snapshot 归一化类型；title 只用于展示。保存完整输入与资源清单，移除当前 `locations.slice(0, 3)` 在决策输入上的截断。保留显式 `unknown` 状态：先补取快照，无法识别的执行/写入请求才一次确认，不能静默退化为普通 local。

依据：[ACP 请求转换](../../electron/agent/acp/adapter.ts#L1698)、[类型判定](../../electron/chat/permission-request.ts#L58)、真实 Claude Bash 描述（安装包源码 `@agentclientprotocol/claude-agent-acp@0.70.0/dist/tools.js:35`；[仓库内验证](../../electron/agent/acp/adapter.test.ts#L987)）、真实请求发送（安装包源码 `@agentclientprotocol/claude-agent-acp@0.70.0/dist/acp-agent.js:4213`；[仓库内验证](../../electron/agent/acp/adapter.test.ts#L987)）。

### F2 · P1：风险规则识别部分语法，不能稳定识别严重后果

**以下分类结果均已用策略探针复现。**

| 操作字符串                                                            | 当前结果 | 与产品目标的关系                    |
| --------------------------------------------------------------------- | -------- | ----------------------------------- |
| `rm -rf /work/shared/client-data`                                     | 确认     | 识别了递归删除                      |
| `rm /work/shared/only-backup.sqlite`                                  | 允许     | 唯一副本是否重要，与文件数无关      |
| `rm -f /work/shared/*.sqlite`                                         | 允许     | 批量删除不需要递归参数              |
| `rsync -a --delete /work/project/empty/ /work/shared/`                | 允许     | 同步可以清空目标已有数据            |
| Python `shutil.rmtree(...)` / Node `fs.rmSync(..., {recursive:true})` | 允许     | 同样后果换解释器写法就未命中        |
| `gh repo delete example/audit-only --yes`                             | 确认     | 专用删除命令已覆盖                  |
| `gh api -X DELETE repos/example/audit-only`                           | 允许     | 同类资源删除经 API 未命中           |
| `psql ... -c 'DROP SCHEMA public CASCADE'`                            | 允许     | 数据库破坏未进入通用确认边界        |
| `docker volume prune -f`                                              | 允许     | 可能删除重要持久化卷                |
| `helm uninstall audit-only`                                           | 允许     | 基础设施风险命令枚举不完整          |
| PowerShell `Remove-Item -Recurse -Force ...`                          | 允许     | POSIX 规则没有形成 Windows 等价保护 |

这些是分类器结果，实际执行仍要求操作系统、数据库或远端凭证具有相应权限。懂 IT 的用户恰恰可能拥有很广的权限，因此“上游允许访问”不能替代误操作保护。

**不建议把所有 Python、Node、脚本、网络调用都改为确认。** 那会破坏产品最有价值的流畅执行能力，而且仍无法完整解释任意程序的副作用。

建议将 shell 识别明确定位为尽力发现高价值事故模式，优先覆盖批量删除、破坏性同步、数据卷清理、数据库清空等常见严重后果；同时在 Wanta 可控的文件和业务执行入口增加结构化操作描述与恢复措施。无法解析的普通脚本仍可自动运行，但产品应承认这层保护有覆盖边界，不能将“没匹配到危险语法”记作“已证明安全”。

依据：[命令风险检查](../../electron/chat/command-risk.ts#L73)、[风险入口](../../electron/chat/command-risk.ts#L399)、[默认兜底](../../electron/chat/local-access-policy.ts#L281)。

### F3 · P1：清理例外把名称与位置当成可恢复性证明

**已复现，置信度高。**

`rm -rf /tmp/another-users-work` 会自动允许，只因为它是 `/tmp` 的直接子目录。`rm -rf /work/project/build` 会自动允许，只因为 `build` 在生成目录名称集合中。

这里没有证明目录由本任务创建、内容可重新生成、存在快照，或没有夹带用户资料。项目名为 `build`、`out`、`target` 的目录也可能存放手工内容。系统是否允许删除其他 OS 用户的文件还取决于权限；即使只影响同一 OS 用户的其他任务，误删也可能造成重大损失。

另一个问题是 `git restore -- only-uncommitted-file.txt` 自动允许；未提交内容不一定能从 Git 恢复。`git restore src` 也自动允许，因为不带末尾斜杠的目录名被当作命名路径，没有读取真实对象类型。

**建议：**

- 当前任务创建且可丢弃的 scratch 内容继续免确认清理。
- 用户已有文件的删除/覆盖优先使用回收站、版本备份或删除前快照；能可靠恢复时自动执行。
- 生成目录在确认来源和内容属性后可以继续自动清理；仅凭目录名不应赋予永久删除豁免。
- `git restore` 等覆盖未提交修改前保存 patch/文件快照，包含未跟踪内容的处理说明；不要假设仓库存在就可撤销一切。
- 无法提供恢复且目标超出已授权范围、包含共享数据或影响范围较大时才确认。

恢复机制不是万能的：普通应用逻辑不能拦截任意脚本的每次系统调用。第一阶段应覆盖 Wanta 控制的写入、删除和已识别命令；需要更强覆盖时再评估快照文件系统或沙箱，避免先搭一个昂贵的全面隔离系统。

依据：[临时路径例外](../../electron/chat/bounded-cleanup.ts#L49)、[生成目录豁免](../../electron/chat/bounded-cleanup.ts#L66)、[Git 路径判断](../../electron/chat/command-risk.ts#L160)。

### F4 · P1：通道信任与操作后果混在一起，业务侧缺少统一兜底

**本地源码与合同确认；远端服务可能另有保护，未在本次核验。**

共享策略对纯 OO 调用直接 `allow`，并将 `highRisk` 置为 false；对可信 host tool 去除重复审批也采用通道归属判断。去除重复审批本身正确，但前提应是更内层真正对后果做过判断。

当前 Link `callAction()` 检查 service/action 格式、缓存 schema、工作空间与连接名称，然后执行；`HostCapabilityKernel` 主要做输入 schema 校验与审计。`destructiveHint` 是工具元数据，并非强制确认机制。外部 OO 合同明确允许 Flow run/publish 不再确认；浏览器则要求购买、发送消息、发布、删除等行为由用户手工完成。

因此：

- “是第一方工具”不能推出“该动作低后果”。
- “账户有权删除”不能推出“用户已授权本次范围的删除”。
- “参数通过 schema”不能证明目标团队、数据量和环境符合用户意图。
- 浏览器对所有外部发送/发布都人工接管，而其他通道宽松放行，既影响流畅度，也难以向用户解释。

**建议：** 保留现有账户、团队和 guard 隔离，在业务执行内层增加少量明确后果类型：普通读取、可撤销写入、外部发送、发布/部署、不可恢复删除、共享或生产变更。先支持产品最常见且后果最严重的连接器，缺少元数据时对明确破坏性操作要求确认，不要把所有未知 Action 都变成硬拒绝。

已明确授权的常规邮件发送、指定环境部署或发布可以一次完成。只有超出对象/环境/数量/金额范围，或者发生不可恢复的大规模破坏，才追加确认。浏览器同步采用这一意图规则；登录、验证码和支付认证仍可作为独立人工步骤，没必要让所有普通“发布”都只能用户手点。

依据：[OO 放行](../../electron/chat/local-access-policy.ts#L212)、[Link 执行](../../electron/agent/link-capability.ts#L159)、[Kernel](../../electron/agent/host-capability.ts#L100)、[业务合同](../../electron/agent/external/oo-capability-contract.ts#L236)、[浏览器行为提示](../../electron/chat/context-system.ts#L194)、[点击执行](../../electron/browser/page.ts#L191)。

### F5 · P1：会话授权覆盖范围与界面承诺不够一致

**匹配问题已复现；原生规则生命周期差异由源码确认。**

`requestMatchesSessionGrant()` 使用 `values.some(...patterns.some(...))`。含多个资源的请求，只要一个匹配就认为整项请求已授权。

探针中，编辑请求同时包含已授权 `/work/project/a.txt` 与宽范围 `/Users/example`：没有 grant 时确认，加入仅匹配前者的 grant 后整项允许。敏感资源和已识别高风险在 grant 前另有保护，因此这不是“任何秘密或危险命令都能用 grant 越过”；问题集中于未匹配资源和后续边界。

另有一个相似的批量语义错误：项目 `.env` 写入判断要求所有资源都是 `.env`。编辑请求同时修改项目 `.env` 和普通源码时，探针返回允许；单独写 `.env` 会确认。

授权生命周期也分裂：

- OpenCode 将 `always` 降为原生 `once`，窄授权保存在 Wanta。
- ACP 将 `always` 传给原生；当前 Claude 包在缺少 suggestions 时可退化为整个工具的 session allow rule，范围可能大于“此命令/此路径”。
- ACP 的 `once` 在原生仅提供 `allow_always` 时会选择后者。当前 Claude 普通请求同时提供两者，因此这一项是通用适配器的条件性缺陷，不是说每次允许一次都会扩大授权。
- `answerPermission()` 在后端回复成功前先写 grant；后端发送失败时，Wanta 侧 grant 没有同事务回滚。用户确已点击授权，但系统会出现界面显示失败、部分授权状态已经生效的分裂。

**建议：** 请求的全部副作用都必须被已有授权覆盖；任一资源敏感则整项检查。会话 grant 由 Wanta 统一持有，包含操作、完整目标范围、工作空间和失效条件；尽可能向原生只回复一次。不能表达一次批准时不能静默升级为永久或更宽授权。授权写入与回复成功需有一致的提交/回滚策略。对于子任务，仅传递其工作所需的授权，并保留来源。

依据：[grant 匹配](../../electron/chat/permission-request.ts#L1114)、[混合 env 写入](../../electron/chat/permission-request.ts#L983)、[授权优先级](../../electron/chat/local-access-policy.ts#L266)、[权限回复](../../electron/chat/node.ts#L3247)、[OpenCode 一次回复](../../electron/agent/opencode-adapter.ts#L93)、[ACP 选项映射](../../electron/agent/acp/adapter.ts#L413)、Claude 授权规则（安装包源码 `@agentclientprotocol/claude-agent-acp@0.70.0/dist/acp-agent.js:4244`；[仓库内验证](../../electron/agent/acp/adapter.test.ts#L987)）。

### F6 · P2：普通环境操作被硬拒绝，审批又不理解已授权意图

**误拒绝已复现，意图缺失由策略输入确认。**

| 操作                               | 当前行为                      | 建议                           |
| ---------------------------------- | ----------------------------- | ------------------------------ |
| `rg OO_API_KEY docs`               | 硬拒绝 `credential_reference` | 检索变量名称不等于读取真实凭证 |
| `printenv LANG`                    | 硬拒绝 `environment_dump`     | 区分明确非敏感变量与整体转储   |
| `env NODE_ENV=test node script.js` | 硬拒绝 `environment_dump`     | 区分环境启动器与打印环境       |
| `git push --dry-run`               | 高风险确认                    | dry-run 应按真实无写入语义处理 |
| 用户明确要求推送后执行 `git push`  | 仍进入相同确认规则            | 复用具体任务授权，避免再次询问 |

前三者在共享 command 分支下，即使完全访问也拒绝，因为 OO 硬拒绝在 full_access 之前。保护宿主管理凭证不应因完全访问消失，但关键字出现不代表真实凭证访问。这也是前一轮 `export PATH` 定向修复后仍会出现同类摩擦的原因。

当前 `LocalAccessPolicyContext` 没有本轮已确认的操作意图或参数范围，因此无法区分“用户刚明确批准了这个动作”和“智能体自行扩大了范围”。

不建议临时加一个泛化布尔值 `userApproved: true`。应记录具体动作及边界，例如“向指定仓库的 feature 分支普通 push”，不能同时授权 force-push、删库或生产部署。机器能验证的字段应由宿主绑定，不能让模型自报已获授权就完全绕过确认。

依赖规则中，选定项目内普通安装免确认、全局或系统修改单独对待是合理的；但用户已选择的内部 registry、正常 requirements 文件等应支持按项目记忆，而不是持续要求改写成分类器喜欢的单条安装命令。

依据：[硬拒绝匹配](../../electron/agent/oo-command-permission.ts#L27)、[环境操作判断](../../electron/agent/oo-command-permission.ts#L136)、[git push 判定](../../electron/chat/command-risk.ts#L170)、[策略上下文](../../electron/chat/local-access-policy.ts#L66)。

### F7 · P2：产品描述、提示词与实现存在多套口径

默认访问 UI 描述为“按智能体的默认审批策略执行”，宿主架构文档却要求 Wanta 拥有统一审批体验。完全访问 UI 描述只说明本地权限，实际注入提示词还会放宽浏览器动作。用户难以判断模式切换到底改变了什么。

另有具体不一致：基础 system prompt 把 broad home/system scans 列在可能暂停边界中；动态默认访问提示和当前分类器则允许非敏感大范围读取。两段同时存在会增加模型先口头求确认的概率，但本文未用模型会话测量这一实际发生率。

权限卡主要展示命令或单个路径，让用户自行推断影响，没有“当前账户/团队、目标环境、对象数量、是否可恢复、为什么超出已有授权”的一致摘要。对懂 IT 的用户，原始命令应继续可见，但主信息应帮助他们核对目标和后果。

建议默认模式文案采用：**“自动执行日常操作；涉及不可恢复删除、重要共享变更或受保护数据时确认。”** 同时在说明中写清 shell 保护尽力而为。完全访问应写明扩大哪些本地和浏览器权限，以及宿主身份/凭证边界仍保留。

依据：[UI 文案](../../src/i18n/app-messages.zh.ts#L989)、[基础提示](../../electron/agent/system-prompt.ts#L65)、[动态提示](../../electron/chat/context-system.ts#L186)、[权限卡](../../src/routes/Chat/PermissionRequiredCard.tsx#L39)。

### F8 · P2：测试主要验证规则，尚未验证产品承诺

这次 208 项测试全部通过，同时上述关键缺陷均可复现，说明测试覆盖面与产品风险并非同一回事。

已有测试对 shell 变体、依赖参数、grant 和自动回复有价值；缺口是：

- 真实原生适配器 payload → Wanta 归一化 → 决策 → 原生回复的完整合同测试。
- 相同后果经不同工具、命令、API 和平台执行的一致性场景。
- 多资源、批量操作、已存在数据、非本任务 scratch、未提交修改等真实对象语义。
- 一次授权不扩大、切换模式/工作空间后的规则生命周期、失败后的授权一致性。
- 产品级误拦截与恢复效果评估。

当前 diagnostics 有按原因统计的 prompts 和自动回复结果；还不足以回答“每百项普通操作打断几次、多少确认重复了用户已给出的授权、多少已识别破坏操作有恢复点、多少请求根本没有经过 Wanta 决策”。

建议扩展匿名/脱敏统计：按适配器和操作类别记录拦截覆盖、用户拒绝/放弃、连续重复确认、unknown 比例、原生未拦截能力声明和恢复成功率。不记录凭证、完整命令参数或私有内容，不为了审计引入新的信息暴露。

依据：[现有诊断](../../electron/chat/permission-diagnostics.ts#L5)、[当前模拟一致性测试](../../electron/chat/local-access-policy.test.ts#L60)。

## 5. 应保留的设计

以下基础值得保留，无需把默认模式改成高频确认模式：

1. **普通本地操作默认自动执行。** 普通脚本、项目检查、数据加工、具体非敏感文件和常规网络请求不需要逐项询问。
2. **共享宿主决策层。** 方向正确，应修正真实输入归一化与未经过宿主的能力声明，而不是给每个 Agent 再写独立策略。
3. **宿主凭证与团队身份边界。** 不允许智能体随意更换 OO 身份、端点和工作空间，能够直接避免“用错别人的账户”。这比对普通命令形式过度敏感更有价值。
4. **任务私有环境和临时目录。** 为依赖安装和中间产物提供清晰落点，能同时提升流畅性与可恢复性。只是“私有归属”不能扩大到整个 `/tmp`。
5. **去掉第一方能力的重复确认。** 保留，但将重要后果检查放在真正的业务执行边界。
6. **自动回复去重、失败恢复、取消语义及模式版本控制。** 已有工程基础有助于减少卡死和状态混乱；应继续与 grant 生命周期统一。

## 6. 推荐的默认访问产品合同

建议先把产品合同收敛为三种处理结果，避免增加大量用户可配置开关。

| 结果         | 操作条件                                                                                    | 用户体验                                              |
| ------------ | ------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 自动执行     | 日常读取、新建内容、范围内可恢复修改、任务自有 scratch 清理、已明确授权的普通业务动作       | 不打断；必要时展示恢复入口                            |
| 明确确认一次 | 超出既有授权范围的不可恢复删除、重要共享/生产变更、未知目标的大范围破坏、直接暴露受保护数据 | 展示对象、账户/环境、范围与可恢复性；确认绑定具体操作 |
| 硬拒绝       | 越过宿主账户/团队隔离、提取 Wanta 托管凭证、调用当前未开放的宿主能力                        | 解释实际边界与可用路径；不提供无效的“允许”按钮        |

决策最少需要以下信息：操作是什么、作用于谁/哪里、影响多大、能否恢复、用户此前明确授权了什么。归一化层还需要区分“已识别普通操作”和“未能识别操作”，避免用同一个 local 标签掩盖未知。

授权对象示例：

```text
动作：清理构建输出
目标：当前项目 /dist，完整规范化路径
范围：本任务生成的对象集合
恢复：可重新构建，或有本次删除前快照
授权有效期：当前任务/指定计划
再次确认触发：目标变为共享目录、对象集合扩大或恢复条件不再成立
```

上述模型不要求模型为每次 `ls`、`cat` 提交庞大 schema。只对有副作用且已进入保护边界的操作收集更完整的信息。对普通脚本保留自动执行，同时明确其属于启发式覆盖；无法从代码文本推导副作用时，不虚构“已验证无风险”。

用户熟悉 IT 的主要意义是可以信任其对明确计划的判断，减少重复确认；它不能保证智能体永远选对路径、账户和对象集合。这里的保护应帮助用户核对智能体的实际执行目标，而非反复确认用户是否愿意完成自己刚提出的任务。

## 7. 推进顺序

### 第一阶段：修正确认链路，不扩大产品复杂度

优先修复 F1 的真实 ACP 归一化、完整资源传递与 unknown 处理；修复 F5 的全量覆盖、混合 `.env` 写入、一次批准不能扩大等授权语义。用真实依赖包 payload 建立合同测试，不只维护手写模拟请求。

同时删除明显的误拒绝：非敏感单变量读取、`env` 启动器、文档中凭证变量名检索和真实 dry-run。统一 UI/提示词描述，让默认访问与完全访问的边界能够准确说明。

验收：真实 Claude 的递归删除请求必须到达风险分支；多个资源不能只匹配一个就放行；同一条已授权操作不因原生回复格式升级为更宽授权。

### 第二阶段：用恢复能力换取流畅性

在 Wanta 能控制的修改和删除入口加入轻量恢复能力；将无来源证明的 `/tmp` 子目录和生成目录永久删除，从自动豁免改为“恢复后自动执行，或一次确认”。高价值误删除命令补充效果识别，按真实目标和变更前状态判断。

验收：删除用户已有重要文件有可验证恢复点；普通构建清理和新文件生成不中断；在真实临时 fixture 中验证恢复，不对用户文件做破坏性测试。

### 第三阶段：统一外部动作与任务授权

先为高频连接器的永久删除、共享数据覆盖、生产部署补充后果描述。把已明确授权的普通发送/发布流程做到一次完成；浏览器、Link、CLI 使用同一份意图与范围说明。需要再次确认的理由应是目标或后果发生变化，而非单纯换了一种工具。

验收：同一个已授权普通动作不因通道切换额外询问；同一个未授权大范围永久删除也不因改走第一方工具而消失确认。对于原生智能体不向宿主报告的执行，明确展示保护覆盖能力，不声称实现了全通道硬拦截。

## 8. 推荐验收场景

| 场景                                                  | 建议预期                                    |
| ----------------------------------------------------- | ------------------------------------------- |
| 读取项目、检索 home 下非敏感文件、处理数据            | 自动                                        |
| 在任务环境安装正常依赖、使用用户已指定的项目 registry | 自动；仅范围扩大再确认                      |
| 清理本任务已创建的中间文件                            | 自动                                        |
| 清理不属于本任务的 `/tmp` 目录                        | 能恢复则自动，否则确认                      |
| 删除唯一原始数据文件或丢弃未提交修改                  | 保存恢复点；无法恢复时确认                  |
| 用户已明确指定仓库/分支的普通 push                    | 复用授权自动执行                            |
| force-push、批量删除共享数据或清空生产数据            | 核对影响计划并确认，绑定具体范围            |
| 用户明确要求向指定收件人发送已确定内容                | 复用授权，避免重复询问；目标/内容扩大再确认 |
| 读取变量名、查看 `LANG`、用 `env` 启动程序            | 自动                                        |
| 提取 Wanta 托管凭证或切换到未授权团队                 | 硬拒绝                                      |
| ACP 请求标题变更、输入分段到达、超过三个资源          | 归一化后与其他适配器一致                    |
| 任一资源未被 grant 覆盖、原生仅提供 always            | 不静默扩大批准范围                          |

建议将这些场景作为后续重构的主验收集。现有命令细节测试继续保留作为实现回归测试，但不再用“又新增多少条规则”衡量功能成熟度。

## 9. 审计交付说明

本次只新增报告与策略探针文本附件，未修改权限实现、提交代码或操作外部资源。工作区原有的 `artifacts/` 及其他审计文件保留原状。

核心决策建议：继续保持默认访问宽松，把强制保护收敛在真实身份边界和重大不可恢复后果上；优先修复真实请求分类与授权范围，再引入可恢复执行。这样才能同时减少不必要的打断和严重误操作的概率。

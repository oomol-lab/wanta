## 1. 总体判断

**这轮完成的是现有权限链路中的关键修复和有限的体验优化，并未完成原报告提出的整体权限重构。**

最明确的成果是：真实 Claude ACP 的命令不再因为标题格式而漏过命令分类；批量请求不能仅凭一个路径匹配就获得整项授权；会话批准不再下放为原生智能体可能更宽的 always 规则；若干正常启动器、环境变量检查和 dry-run 从误拦截改为自动执行。

原报告中更大的设计问题仍然存在：默认策略主要识别命令语法，尚不能稳定判断损失程度、数据归属或恢复能力；连接器、CLI 与浏览器也没有形成统一的业务后果与任务授权机制。

因此，当前可以对外表述为：**“修复了已确认的权限漏判和误拦截，保持日常操作自动执行。”** 不应表述为“默认访问安全问题已全部解决”“已经实现可恢复执行”或“所有智能体、所有通道的保护都相同”。

## 3. 已完成的具体事项与证据

### 3.1 修正真实 ACP 请求分类

权限请求优先从 `kind: execute` 或具体 `rawInput.command` 识别命令，不再要求标题包含 Bash/command/shell。结构化 read/edit 也作了相应转换。分段到达的 kind、title、rawInput、locations 从现有 live tool snapshot 补齐，不新增查询或等待。

此前的 `locations.slice(0, 3)` 已移除。这里的“完整”指完整保留智能体实际上报的资源，不代表 Wanta 能推导脚本内部所有隐式文件访问。

真实 Claude payload 测试覆盖普通 `node process.js` 自动允许、递归删除进入确认、`printenv` 整体转储拒绝；分段请求测试覆盖第四个路径是 `.env` 的情况。

代码：[ACP 请求转换](../../electron/agent/acp/adapter.ts#L1717)、[内存补齐](../../electron/agent/acp/translator.ts#L395)。测试：[真实 Claude payload](../../electron/agent/acp/adapter.test.ts#L987)、[第四个敏感路径](../../electron/agent/acp/adapter.test.ts#L1012)。

**未完成部分：** 输入仍无法识别时，代码保留 title/permission 回退，共享分类器仍可把它归为 local 并允许。本次复核对 `action: permission` 的空资源请求得到 allow。因此，不能把 F1 扩大为“未知请求已安全处理”。

### 3.2 修正授权范围，并减少重复确认

已有授权必须覆盖当前请求的全部待匹配值；同一操作类型的多个已有窄授权可以联合覆盖批量请求。这样既防止范围扩大，又避免用户已分别批准多个路径后，在批量处理时再次批准。

混合编辑只要包含所选项目 `.env`，就进入对应写入检查，不再要求所有资源都是 `.env` 才触发。

ACP 的 once/always 都选择原生 allow_once，会话 grant 由 Wanta 持有。原生只有 allow_always 时返回 cancelled，不把一次批准升级成宽授权。后端回复成功后才记录新 grant，防止发送失败留下已生效授权。

代码：[授权合并](../../electron/chat/local-access-policy.ts#L153)、[全量匹配](../../electron/chat/permission-request.ts#L1114)、[env 写入检查](../../electron/chat/permission-request.ts#L983)、[原生批准选项](../../electron/agent/acp/adapter.ts#L413)、[成功后记录授权](../../electron/chat/node.ts#L3247)。测试：[授权覆盖](../../electron/chat/local-access-policy.test.ts#L87)、[失败后不保留 grant](../../electron/chat/node.test.ts#L4022)。

**未完成部分：** 通用 grant 仍以 action/patterns 为主，未新增统一工作空间标识、过期模型或子任务最小授权模型。对已存在的原生授权规则，也没有迁移或清除流程。只支持原生 always 的请求虽不会被扩大批准，但“为什么取消、用户如何继续”的体验尚未专门完善。

### 3.3 放行明确的普通环境操作

以下场景已由拒绝/确认改为自动执行：

- `env NODE_ENV=test node script.js` 等普通启动器；仍检查内部实际命令。
- `printenv LANG`、`printenv PATH HOME` 等当前白名单中的非敏感变量。
- `rg OO_API_KEY docs`、`grep` 字面名称搜索，以及覆盖到的 cd/普通 shell 包裹形式。
- `git push --dry-run` / `-n`。

真实凭证值引用、整个环境转储、宿主运行时身份/配置修改仍保留保护。这里是若干明确形式的放行，不是“任意环境变量检查都已放开”；例如 `env -S` 仍不属于普通启动器例外。

代码：[环境操作判断](../../electron/agent/oo-command-permission.ts#L136)。测试：[普通操作免确认](../../electron/chat/local-access-policy.test.ts#L22)。

### 3.4 补充少量高后果命令

删除目标多余内容的 rsync、Docker 数据卷 prune、Helm uninstall 已进入命令风险检查。普通 rsync 及识别到的 rsync dry-run 保持自动执行。

这些是现有分类器中的有限补充，**仍属于语法规则，不是原报告设想的统一操作后果模型**。并未实现所有删除路径、解释器或业务 API 的覆盖。

代码：[命令风险判断](../../electron/chat/command-risk.ts)。

### 3.5 清理 cwd 与轻量性能优化

清理命令现在使用请求已携带的真实 cwd；符合原有生成目录豁免的 `rm -rf dist` 不必再重复写 `cd`。共享策略去掉一次重复风险计算；环境解析增加快速排除分支。

**这项改变解决的是流畅性，不能计作 F3 的安全修复。** `/tmp` 子目录和生成目录名称豁免仍存在，cwd 识别增强还使更多等价写法能够使用原来的豁免。

代码：[清理目标解析](../../electron/chat/bounded-cleanup.ts#L93)、[共享入口](../../electron/chat/local-access-policy.ts#L300)。测试：[cwd 与项目匹配](../../electron/chat/local-access-policy.test.ts#L75)。

### 3.6 文案和验证

默认访问说明已改成“自动执行日常操作，敏感数据或已识别的高风险操作需要确认”。基础提示词把大范围读取与宽范围编辑区分开，并同步新增规则。OO 启动器指引移到 Link 专用段，避免进入无 Link 的本地模式提示。

完全访问说明和权限卡结构未改造。没有增加新权限模式、产品设置项、自动备份系统或模型风险判定器。

## 5. “不更卡、不增加普通操作确认”的落实程度

### 已有证据支持的结论

- 继续使用既有宿主策略，没有引入新的权限服务或审批流程。
- 请求补齐复用内存快照，分类器没有新增网络查询、磁盘扫描或模型调用。
- 普通脚本、常规项目依赖、已覆盖的环境操作、dry-run、正常文件读写和清理场景有回归用例。
- 会话 grant 支持联合覆盖，避免把完整性修复变成重复确认。

### 性能数据及其边界

上一轮本地微基准对基线与优化版本分别测量 21,000 次调用，采用多批次平均单次耗时的中位数：

| 指标                         | 基线        | 优化后                  |
| ---------------------------- | ----------- | ----------------------- |
| 策略平均单次耗时的批次中位数 | 约 0.063 ms | 约 0.071 ms             |
| 差值                         | —           | 约 +0.008 ms，即 8 微秒 |

该数据支持“这批场景中策略计算开销很小”，**不支持“算法更快”或“完整会话延迟绝不会增加”**。语料还包括原先会提前拒绝、现在执行完整放行路径的操作，不能把差值全部解释为相同决策路径的退化。

这不是 UI 帧耗时、P95 延迟或真实智能体长任务测试。原生 always 改为宿主记忆后，后续请求可能多一次原生与宿主之间的本地权限往返，虽然正常情况下用户不会看到弹窗，其端到端成本没有单独测量。当前尚无线上打断率数据。

### 确实会增加确认或改变继续方式的场景

- 原先因 Claude 标题格式漏掉的高风险命令，现在会进入原有确认/拒绝分支。
- 批量请求有未获授权的范围，或混合请求包含 `.env` 写入时，会正确确认。
- 新增的破坏性同步、数据卷清理、Helm 卸载会确认。
- 原生仅提供 allow_always 时，单次批准不会升级，而是取消该请求。

因此更准确的承诺是“减少已覆盖普通操作的误打断，恢复少量必要边界”，而不是“不论做什么，弹窗总数都不可能增加”。

## 8. 后续建议：保持小范围，不一次性推进全部架构建议

1. **先验证当前修复的真实体验。** 用真实 Claude/Codex 跑普通文件加工、项目检查和重复窄授权场景，测实际确认次数与等待时间，尤其检查原生 only-always 和长会话 grant 的行为。
2. **优先决定 `/tmp` 清理豁免是否符合产品定位。** 这是仍直接关联“删掉其他任务资料”的缺口。下一步可以只围绕这一规则做受控范围和兼容性评估，不必先实现全面备份系统。
3. **补齐低成本的用户说明。** 说明完全访问对浏览器的影响，以及默认保护的启发式覆盖边界；无需先重做权限卡。
4. **根据真实任务再选择业务场景。** 若高频任务涉及共享资料批量删除或生产发布，再针对该入口设计最小保护。暂不为所有连接器构建统一风险引擎，也不将所有脚本改为审批。

当前交付的主要价值已经成立：修复关键链路错误并减少已确认的日常误拦截。后续应优先验证这些收益，并针对剩余具体风险做小步调整，而不是将原报告中的所有架构建议都当成必须一次实现的清单。
